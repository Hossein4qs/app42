# نقشه‌ی راه پروژه‌ی App 42

> زمان‌بندی‌ها تقریبی و برای یک توسعه‌دهنده‌ی نیمه‌وقت (حدود ۱۰ تا ۱۵ ساعت در هفته) است. بر اساس تیم و زمان خودت مقیاسش را تغییر بده.

## فاز ۰: آماده‌سازی (هفته ۱)

**هدف:** قبل از تغییرهای بزرگ، مطمئن شوی چیزی خراب نمی‌شود.

- [ ] ساخت شاخه‌ی `develop` و تعیین قوانین merge
- [ ] فعال‌سازی Renovate یا Dependabot
- [ ] ثبت حجم باندل فعلی با `rollup-plugin-visualizer` برای مقایسه‌ی بعدی
- [ ] نوشتن فهرست ابزارهای موجود و وابستگی هر کدام به APIهای تلگرام

**معیار تکمیل:** وضعیت فعلی (حجم باندل، فهرست ابزارها، وابستگی‌ها) مستند شده است.

## فاز ۱: امنیت و حریم خصوصی (هفته ۲ تا ۳)

**هدف:** حساس‌ترین بخش پروژه، یعنی Session String، را محکم کنی.

- [ ] رمزنگاری Session در IndexedDB با Web Crypto API
- [ ] حذف `crypto-js` و جایگزینی با Web Crypto
- [ ] دکمه‌ی «خروج و پاک‌کردن کامل داده‌ها»
- [ ] نمایش و ابطال نشست‌های فعال
- [ ] بازبینی رویدادهای `react-ga4` و حذف هر داده‌ی مرتبط با چت یا کاربر
- [ ] صفحه‌ی حریم خصوصی (چه داده‌ای کجا ذخیره می‌شود)

**معیار تکمیل:** هیچ Session یا داده‌ی حساسی به‌صورت متن ساده ذخیره نمی‌شود و کاربر با یک کلیک همه‌چیز را پاک می‌کند.

## فاز ۲: ارتقای زیرساخت (هفته ۴ تا ۶)

**هدف:** از وابستگی‌های قدیمی خلاص شوی، به ترتیب ریسک. هر مورد در یک PR جداگانه و با تست دستی داخل تلگرام.

1. [ ] مهاجرت `@telegram-apps/sdk-react` به SDK جدید `@tma.js` (بیشترین ریسک، اول انجام بده)
2. [ ] ارتقای `@telegram-apps/telegram-ui`
3. [ ] ارتقای Vite
4. [ ] مهاجرت به ESLint 9 (flat config) و typescript-eslint 8
5. [ ] بررسی React 19 و react-router جدیدتر، فقط اگر وابستگی‌ها پشتیبانی کنند
6. [ ] ارزیابی جایگزین برای `telegram` (GramJS): npm اعلام کرده این پکیج بایگانی شده و دیگر نگهداری نمی‌شود. تا زمانی که جایگزین بررسی و آزمایش نشده، همین نسخه را با نسخه‌ی دقیق (بدون `^`) نگه دار.

> قبل از هر ارتقا، آخرین نسخه‌ی پایدار و راهنمای مهاجرت (migration guide) را بررسی کن.

**معیار تکمیل:** `npm run build` بدون هشدار اجرا می‌شود و همه‌ی ابزارها داخل Telegram کار می‌کنند.

## فاز ۳: تست و CI (هفته ۷ تا ۸)

**هدف:** ارتقاها و تغییرهای بعدی را بدون ترس انجام بدهی.

- [ ] نصب Vitest و نوشتن تست برای منطق خالص (محاسبه‌ی آمار، پردازش داده‌ها)
- [ ] چند تست E2E با Playwright برای مسیرهای اصلی، با mock کردن Telegram API
- [ ] اضافه‌کردن مرحله‌ی تست به workflow موجود در GitHub Actions
- [ ] بررسی `strict` بودن TypeScript و حذف `any`ها

**معیار تکمیل:** هر PR به‌طور خودکار lint، type-check و تست می‌شود.

## فاز ۴: عملکرد و پایداری (هفته ۹ تا ۱۱)

**هدف:** برنامه روی گوشی‌های ضعیف هم روان باشد.

- [ ] Lazy-load برای GramJS، lottie-react، jszip، chart.js و react-multi-date-picker
- [ ] بارگذاری جداگانه‌ی هر ابزار (route) با `React.lazy`
- [ ] انتقال تحلیل‌های سنگین به Web Worker
- [ ] Virtualization برای لیست‌های بلند (مخاطبین، پیام‌ها، چت‌ها)
- [ ] کش در Dexie با سیاست مشخص invalidation
- [ ] مدیریت `FLOOD_WAIT` با صف، backoff و نمایش پیشرفت
- [ ] قابلیت لغو و ادامه برای عملیات طولانی
- [ ] ErrorBoundary و گزارش خطا (بدون ارسال داده‌ی حساس)

**معیار تکمیل:** حجم باندل اولیه حداقل ۳۰ تا ۴۰ درصد کمتر از فاز ۰ است و عملیات طولانی هیچ‌وقت UI را قفل نمی‌کند. این عدد را بعد از اندازه‌گیری واقعی تنظیم کن.
